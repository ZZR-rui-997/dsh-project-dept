# loop-ops — 自动改稿/审稿闭环

> 设计模式来源：ARIS 的 `auto-paper-improvement-loop`（MAX_ROUNDS + 防谄媚审稿）与
> `auto-review-loop`（REVIEW_STATE.json 状态链）。这里只借**模式**，不搬它的 Codex/Gemini
> MCP 后端；审稿人用当前 Harness 的 subagent 机制。

它是 project-dept 的**循环执行器**，不是验收标准：循环产出仍是 L2 产物，最终是否算完成，
仍由 project-dept 的 L3（Lead 汇总 + 用户过目）判定。

## 一、何时用 / 何时不用

**用**：

- 一份已成形的东西（章节、文档、代码、图件清单）要"多轮打磨到没有硬伤"；
- 用户明确说"自动改稿 / 过夜跑 / 改稿循环 / 审稿循环"；
- 工作量集中在"发现问题 → 逐条修"上，且修完能自动复验。

**不用**：

- 首轮写作（先走命题/结构那一步，别拿循环代替构思）；
- 板块验收（那是 project-dept 的三层验收，人工触发、不循环）；
- **用户没发令**——本 skill 永不自行启动；
- 没有可判定的验收标准（先补标准，再谈循环）。

## 二、四件设计模式（不可裁剪）

### 1. 轮次硬上限

- 默认 `MAX_ROUNDS = 2`；用户显式要求时最多放宽到 3，**不允许更多**。
- 经验依据：第一轮多在修结构与事实，第二轮在修表达与一致性，两轮之后边际收益明显下降，
  第三轮往往开始"为改而改"（把对的句子改错）。
- 每轮预算 = 审稿（1 次深读）+ 修改（主线程）+ 复审（1 次核对）。

### 2. 防谄媚审稿（fresh-thread 原则）

- **每轮审稿必须新开 subagent**（每次新 `name`），禁止复用上一轮的 reviewer——它记得
  "作者改了什么"，会手软。
- 审稿 prompt 里**禁止**出现"上一轮我们改了什么 / 上一轮得了多少分"；只给当前稿子 + 岗位卡。
- 反例（这条为什么值钱）：复用线程会把真实的 3/10 虚高成 8/10。
- reviewer prompt 开头 = 岗位卡全文（如 `_team/岗位/reviewer.md`），并写明"默认有错，
  至少给出 1 个真问题"，输出必改项格式 **位置 + 现文 + 应为 + 依据**。
- **审稿人崩溃防护**：①一次只派一个审稿任务；②等结果，超时视为崩溃 → 换新 name 重派一次；
  ③二连崩 → 落盘"复核人崩溃"记录，**降级为主线程用另一种方法自证**（异方法交叉核对），
  不得直接标通过。

### 3. 状态落盘（可恢复）

每轮结束写 `loop_state/<task_id>/REVIEW_STATE.json`：

```json
{
  "task_id": "…",
  "target": "被审对象（文件路径或交付物名）",
  "round": 2,
  "max_rounds": 2,
  "reviewer_agent": "rev-<task>-r2",
  "score_this_round": 7,
  "must_fix": ["位置 + 现文 + 应为 + 依据", "..."],
  "edited_files": ["..."],
  "whitelist": ["本轮允许改的文件"],
  "next": "review|edit|done"
}
```

上下文被压缩、会话被续接之后，**先读这个文件再决定下一步**，不凭记忆续跑。

### 4. 编辑白名单

- 发令时第一步就定下本轮允许修改的文件清单（例如只允许改 `第4章.md` 与 `图2-3.png`），
  逐轮记进 REVIEW_STATE。
- 修改**不得越出清单**；要扩清单必须停下来问用户。
- 白名单是防"顺手重写"的刹车：循环最容易的失败方式不是没改对，而是把没让改的地方也改了。

## 三、流程（六步）

```
1  发令确认：目标文件、MAX_ROUNDS（默认 2）、白名单、评分口径、验收器命令
2  Round n 审稿：新 subagent（name=rev-<task>-r<n>）读稿 → 必改项列表（位置+现文+应为+依据）
3  Round n 修改：主线程按必改项逐条修（只动白名单）→ 跑验收器
   （正文→对应 check_*.py；图→图件验收器；都过才进第 4 步）
4  复审：**新 subagent**（name=rev-<task>-r<n>b）只回答"必改项是否全部落地 + 有没有新硬伤"；
   复审不打分（防分数游戏）
5  收敛判定：复审全过 → 落盘 next=done 并报告；否则 n+1 ≤ MAX_ROUNDS 回第 2 步；
   超限 → 停下如实报告剩余问题，**不得自动放宽判据**
6  交回用户：终稿 diff 摘要 + 每轮审稿单路径 + REVIEW_STATE
```

## 四、红线

- **交付 ≠ 完成**：循环跑完只是 L2 产物，仍需 L3（Lead 汇总 + 用户过目）。
- **一次只做一个循环**：本循环就是当前板块的工作，不并行开第二个。
- **不编数**：分数与必改项必须落盘可查；复审说"已落地"要引用行号。
- **永不静默放宽**：轮次用尽仍有问题 → 停下报告，让用户决定（加轮 / 降标准 / 人工收尾）。
- **验证器优先于审稿人**：能用脚本判定的（格式、引用、数值一致性、图件尺寸）先交给脚本，
  审稿人只判脚本判不了的（论证、结构、可信度）。

## 五、工具对接（当前 Harness）

| 环节 | 工具 | 备注 |
| --- | --- | --- |
| 派审稿人 | `subagent` | 每次新 `name`，prompt = 岗位卡全文 + 目标 + "默认有错" |
| 等结果 | `subagent` 返回即收 | 超时按崩溃预案；二连崩 → 主线程异方法自证 |
| 修改 | `edit` / `write` | 只动白名单；改完立刻跑验收器 |
| 状态 | `write` REVIEW_STATE.json | 每轮必写；压缩后靠它续跑 |
| 台账 | 看板 + 交付登记簿 | 循环结束时统一记，不逐轮记 |

## 六、与 project-dept 的分工

| 问题 | 归谁 |
| --- | --- |
| 这一版该不该交付 | project-dept（三层验收 + 独立盲审） |
| 这一版还有哪些硬伤、怎么逐条修完 | loop-ops |
| 修复后有没有引入新问题 | loop-ops 的复审（新线程） |
| 修完能不能标完成 | project-dept 的 L3（Lead + 用户） |
