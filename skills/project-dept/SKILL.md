# project-dept — 项目部：一次只做一个板块

这不是"多开几个 agent 并行干活"的说明书，而是一套**承包制**：项目部（Lead + 队员）一次只接一个板块，做完、验完、归档，再接下一个。

核心命题只有一句：**能调度不等于做对**。调度是宿主的能力，判断对错是这套规程的责任。

## 何时加载

- 用户要求"按项目部开工 / 开个板块 / 组团队做这块 / 走流程"；
- 一件工作大到要拆给多人（或跨多轮），且**交付物要可验收**；
- 用户强调"检查要独立、别自己人验证自己人"；
- 要写进正式交付物（论文正文、结题报告、上线代码、对外文档）之前。

## 何时不加载（不适用，别硬套）

| 场景 | 为什么不用 |
|---|---|
| 单文件小改、一次性查询、纯解释性问答 | 开板块的成本大于收益（口径：见 `references/self-skepticism.md` 优化准入） |
| 没有可判定验收标准的探索 | 验收标准写不出来就不该开工，先做需求澄清 |
| 需要**实时**拦截的场景（写文件当场拒绝） | 这是宿主的机制层职责，规程管不了，见 `references/mechanism-choice.md` |

## 路由协议（动手前五步）

1. **读清单与核心层**：读 `manifest.yaml`，再读它 `always_load` 列的文件。不要先读 `references/`。
2. **定轴值**：按 `manifest.yaml` 里每个轴的 `detect:` 提示判断本次的两个轴值，然后**用一行把检测结果告诉用户**，让他能低成本纠正——这是进度同步，不是审批闸门。
3. **只加载命中的片段**：按轴值读 `static/fragments/` 里对应的文件。**不要读 `static/` 里所有片段**。
4. **按优先级套用**：core stance（`static/core/principles.md`）→ 交付物片段 → `static/core/workflow.md` 六步 → `static/core/output-contract.md` 输出契约。
5. **按需取深参**：只有触发 `manifest.yaml` 里 `references.on_demand` 的条件时才读对应文件。

**声明了却读不到的文件是缺陷，不是"跳过继续跑"的理由**：`manifest.yaml` / 本文件里声明要读的任何一个文件不存在，立刻停下、把缺失路径原样报给用户并记录，不许静默跳过、也不许凭记忆替它补内容。声明与实体不一致本身就说明这个包坏了（见 `references/anti-patterns.md`）。

## 三条不可协商

| # | 原则 | 反面（禁止） |
|---|---|---|
| 1 | **一个板块一个板块做**，同一时刻只有一个 active | 把一件工作横切成几块同时推进 |
| 2 | **检查必须由局外人独立做**，不参照已有成果 | 拿"和旧版一致 / 和历史结论一致 / 作者说跑通了"当证据 |
| 3 | **完整闭环**：立项 → 拆解 → 执行 → 交付 → 验收 → 归档 | 干完自己标"完成" |

## 边界：本 skill 管什么、不管什么

- **管**：怎么组织人与验收、什么算完成、拿什么当基准、错了怎么处置。
- **不管**：专业内容口径（交给对应领域的 skill）、具体工具的实操（交给对应工具的 skill）、桌面/GUI 操作（交给桌面操作类 skill）、宿主机制的实时拦截（交给宿主插件）。
- 若一个诉求属于"约定/流程/判据"，落本 skill；若属于"某个专业的具体参数与写法"，落项目侧。

## 项目落地（一次性，之后只填内容）

本 skill 是**通用骨架**；每个具体项目在自己的工作目录里填四样东西：

1. `AGENTS.md`（或等价的自动注入文件）：这个项目是什么 + 硬规则摘要 + 指向项目台账；
2. 台账目录（默认 `_team\`）：章程、流程、看板、登记簿、岗位卡、模板、产物；
3. `dept.config.json`：把本项目路径与专用名词填进配置，**不许写进脚本**；
4. 专业岗位卡与基准清单：本领域要盯的坑、可当基准的条目及其出处。

脚本一律**相对自身位置解析**，不写死绝对路径。但注意：`find_config` 从**当前工作目录**向上找 `dept.config.json`，若在项目目录树之外运行可能找到错误项目的配置 —— 跑闸门前先确认 cwd 在本项目内，或显式传 `--config` / `--root`（R3-P4，如实声明而非假装无 cwd 依赖）。
